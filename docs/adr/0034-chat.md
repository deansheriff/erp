# 0034. Chat: conversations, membership and real-time updates

- Status: Accepted
- Date: 2026-11-27

## Context

Phase 12 adds collaboration (brief sections 7 and 9.14): direct messages, group chats and
department channels, with:

- attachments through the files service;
- reactions, pins, mentions, read receipts and unread counts;
- real-time updates over WebSockets fanned out through Redis.

Every action has to check that the actor is a current member of the conversation.
WebSockets authenticate with the session cookie, check the origin, re-validate the
session and close on revocation. The product owner settled the business rules on
2026-11-27.

## Decisions

**Module.** The work goes in `app/modules/chat`, with real-time delivery in
`app/realtime`, a core package beside `app/mail` that any module may use.

**Conversations** come in three kinds, and every member is a user account.

- **Direct.** Exactly two people. There's one per pair, and it can't be left.
- **Group.**
  - Any employee with chat can start one, with a name.
  - The creator is its admin and can make others admins.
  - Admins add and remove members and rename it. Anyone can leave.
  - When the last admin leaves, the longest-standing member becomes admin.
- **Department channel.**
  - There's one for each active department.
  - Membership comes from the org chart: everyone with an account who currently holds a
    position (primary, acting or interim) in the department or a sub-department.
  - Membership is synced by a task every 10 minutes, and for the viewer whenever they
    open chat. Nobody joins or leaves by hand.
  - A deactivated department's channel becomes read-only.
  - **Moderators** are the current holders of the department's top positions (those
    whose parent sits outside the department), plus anyone with `chat.channel.moderate`.

**Membership is the access rule.** Every read and action checks for a current
`chat_members` row: listing, reading, sending, editing, deleting, reacting, pinning,
marking read and downloading an attachment. A non-member gets "not found", so the
response doesn't reveal that the conversation exists. Members see the whole history;
leaving or being removed loses access to all of it.

**Messages.**

- A message has text (up to 4,000 characters) and optional attachments.
- **Edits:** the sender can edit within 15 minutes, and the message shows as edited.
- **Deletes:** the sender can delete their own at any time. Group admins and channel
  moderators can delete anyone's. A deleted message keeps its place as "Message
  deleted", and its text, attachments, reactions and pin go.
- **Reactions:** a fixed set (👍 ❤️ 😂 🎉 😮 🙏), toggled by any member.
- **Pins:** any member can pin or unpin, and the pin records who pinned it.
- **Mentions:** `@` followed by a member's full or first name. They're resolved against
  the conversation's members, stored, and highlighted.

**Read receipts and unread counts.**

- Each member has a last-read message (message ids are UUIDv7, so they sort by time).
  Opening a conversation, or receiving new messages while it's open, moves it on.
- **Unread** means messages after it from someone else, not deleted.
- **Receipts:** under the latest message, direct messages and groups show who has seen
  it. Department channels show only "Seen by N".

**Email.**

- A task runs every 5 minutes. It emails anyone with a mention, or a direct message,
  still unread after 30 minutes.
- At most one email goes per person, per conversation, per day.
- The email names the conversation and the sender, and never includes the message text.

**Settings.**

- The edit window (15 minutes) and the email delay (30 minutes) are editable, to confirm.
- Retention is "kept indefinitely" until an administrator sets a number of days, to
  confirm. When set, a daily task deletes messages, and their attachments, older than
  that.

**Attachments** use file purpose `chat_attachment`, attached to the message, up to
25 MB of images, PDFs, Office documents and text files (CSV included).

- **New in the files service:** a purpose may name an **access check**
  (`FilePurpose.allow`), which runs as well as the permission.
- **Attaching:** the sender owns the attachment, so it needs `chat.conversation.use`
  for oneself.
- **Viewing:** decided by chat's access check alone, which needs the downloader to be a
  current member of the message's conversation. No permission scope applies.
- **Deleting a message:** its files are removed as a system deletion, since the delete
  is already authorised.

**Real-time.**

- **The socket only carries notices.** `/ws/chat` sends small events naming a
  conversation and what changed: a new message, a change, read, unread or membership.
  It never carries message content. The page then fetches the HTML through ordinary
  routes, which check membership and permissions as usual, so authorisation lives in
  one place.
- **Fan-out:** each user has their own channel (`user:{id}`). Services publish to the
  members' channels after the transaction commits, so a rolled-back change sends
  nothing.
- **Brokers:**
  - **Redis** pub/sub works across processes and is required in production. Start-up
    refuses a production configuration that uses the memory broker.
  - **An in-process memory broker** is for tests and single-process development
    (`KX_REALTIME_BACKEND=memory`).
- **The socket endpoint:**
  - It's the only `async def` handler (ADR 0004). Database work runs in a worker thread.
  - It refuses a connection with an Origin other than the site's own.
  - It resolves the session cookie as any page does, and needs `chat.conversation.use`
    with MFA satisfied.
  - Its re-checks don't count as activity, so an open tab doesn't keep an idle session
    alive.
  - It re-validates the session every 60 seconds.
- **Revocation.** Identity publishes a "sessions revoked" event to the user whenever it
  revokes their sessions: sign-out, revoking a session, a password change or reset,
  suspension and exit. Every open socket of that user re-checks its own session at once
  and closes with code 4401 if it's gone.
- **Fallback.** With no socket, the page still works: sending posts a form, and the list
  refreshes on navigation.

**Permissions.**

| Permission | Who has it |
|---|---|
| `chat.conversation.use` | Every employee, for themselves (the Employee role), which keeps that role self-service only; membership decides which conversations |
| `chat.channel.moderate` | Organisation Administrators: delete any message in a department channel |
| `chat.settings.manage` | Organisation Administrators |

## Consequences

- Section 9.15 (notifications and the approvals inbox) is not part of this phase. Chat
  sends its own unread emails through the mail outbox.
- The route-declaration check covers HTTP routes. A separate test pins the WebSocket
  routes to `/ws/chat` and exercises its checks.
- The screens were requested from Stitch and are marked `stitch_pending` until they
  arrive.
